Bong Bong (1989, Lee T.K. / Yonsei COMSCI)  -  BONGBONG.EXE 역어셈블 & C 변환
=============================================================================

[결과물]
  bongbong.c         역컴파일한 C 소스 (함수 33개 전부, 역할에 맞는 이름으로)
  bongbong_smooth.c  같은 게임을 부드럽게 그리도록 고친 판
  tp.h / tp.c        터보 파스칼 Graph/Crt/Dos/System 호환 층 (djgpp 용)
  bongbong.mak       djgpp 빌드
  listing.asm        주석 단 어셈블리 (원본 대조용, 3,556줄)
  README_DECOMP.txt  이 문서


[빌드]
  ..\..\djgpp.bat 로 창을 연 뒤 이 폴더에서

      make -f bongbong.mak            -> BONG.EXE   원본에 충실한 판
      make -f bongbong.mak smooth     -> BONGS.EXE  부드럽게 움직이는 판
      make -f bongbong.mak all        둘 다
      make -f bongbong.mak clean

  (bongbong.mak 을 makefile 로 이름만 바꾸면 그냥 make 로도 된다)

  원본 BONGBONG.EXE 를 덮어쓰지 않으려고 결과물 이름을 다르게 했다.
  실행에 필요한 파일
      BONG.EXE   : CWSDPMI.EXE, 16X16.DAT, B_ST.DAT
      BONGS.EXE  : 거기에 더해 HSMALL.FNT, ESMALL.FNT (한글 글꼴)
  (djgpp 로 만든 프로그램은 DPMI 호스트가 필요해서 CWSDPMI.EXE 를 같이 둔다.
   CGA.BGI 는 이제 안 쓴다.)

  ※ djgpp 는 32비트 보호모드라 16비트 BGI 드라이버(CGA.BGI)를 부를 수 없다.
    그래서 원본이 쓰던 파스칼 런타임 함수를 tp.c 에 같은 이름·같은 의미로
    다시 구현했다.  bongbong.c(게임 로직)는 손대지 않아도 된다.

        Graph  -> VGA 모드 13h(320x200x256) 프레임버퍼 직접 접근.
                  DAC 0..3 번만 CGA 팔레트1(검정/밝은청록/밝은자홍/흰색)로
                  맞춰서 원본 CGA 4색과 같은 화면이 나온다.
                  글자는 BIOS ROM 8x8 글꼴(int 10h AX=1130h)을 쓴다.
                  GetImage/PutImage 버퍼는 BGI 와 같은 머리(폭-1, 높이-1)를
                  두되 픽셀은 1바이트씩 담는다 - ImageSize 도 그에 맞췄다.
        Crt    -> 키보드 int 16h (확장키는 0 + 스캔코드 두 번에 나눠 준다),
                  소리는 8253 채널2 + 포트 61h.
        Dos    -> GetTime/SetTime 은 진짜 시스템 시계를 건드리지 않고
                  uclock() 기반 가상 시계로 흉내낸다.  원본이 1초마다
                  SetTime(0,0,0,0) 으로 시계를 되돌리기 때문에 이게 필요하다.
        Crt.Delay -> 원본(터보 파스칼)의 Delay 는 프로그램이 뜰 때 재 둔 빈 루프
                  횟수로 기다린다.  그래서 기계가 빠를수록 실제 대기 시간이
                  짧아지고(빠른 기계에서는 사실상 0), 게임이 눈 깜짝할 사이에
                  지나간다.  여기서는 PIT 를 읽는 uclock() 으로 진짜 시간을
                  재므로 어떤 기계에서도 정확히 그 시간을 기다린다.
        System -> 텍스트 파일 읽기(Assign/Reset/ReadChar/ReadInt/Readln/Close),
                  GetMem, Str, Delete, Halt.
                  ReadChar 는 파스칼처럼 줄 끝에서 CR(#13)을 돌려주고
                  줄을 넘어가지 않는다 - 16X16.DAT/B_ST.DAT 를 읽는 방식이
                  이 동작에 기대고 있다.


[기계가 빨라도 같은 속도로 - 원본과 달라진 유일한 곳]
  원본이 빠른 기계에서 미친 듯이 빨라지는 이유는 두 가지다.

    1) 터보 파스칼 Delay 가 빈 루프 방식이라 기계가 빠를수록 짧아진다.
       -> tp.c 의 Delay 를 uclock()(PIT 를 직접 읽는다) 기준으로 바꿨다.
          Delay(250) 은 어떤 기계에서도 정확히 250ms 다.

    2) GameLoop 이 아무 제한 없이 최대 속도로 돈다.
       -> tp.c 에 FrameSync(fps) 를 넣고 GameLoop 첫 줄에서 부른다.
          루프가 초당 GAME_FPS(70)번으로 묶인다.  너무 밀리면 다시 맞춘다.
          기다리는 동안 __dpmi_yield() 로 CPU 를 양보하므로 도스박스에서
          100% 를 물고 있지 않는다.

  적/발판 이동과 남은 시간은 원본부터 이미 시계(GetTime)로 재고 있어서
  손대지 않았다.  즉 bongbong.c 에서 원본과 다른 곳은 GameLoop 의
  FrameSync 한 줄뿐이고, 나머지는 tp.c 쪽 구현 문제다.

  속도를 바꾸고 싶으면 tp.h 의 GAME_FPS 만 고치면 된다.

[원본이 무엇인가]
  볼랜드 **터보 파스칼**로 만든 16비트 리얼모드 DOS 프로그램이다. (C 가 아니다)
  근거: 문자열이 전부 길이 접두 파스칼 문자열이고, Graph(BGI)/Crt/System 유닛을
  far call 로 부르며, 6바이트 real 타입을 쓴다.
  화면은 BGI CGA 드라이버로 320x200.  압축(EXEPACK 등)은 걸려 있지 않다.

[실행 파일 구조]  (MZ 헤더 512*... 뒤 이미지 기준, 진입점 CS:IP=0000:2602)
  0x0000..0x268F   주 프로그램 : 게임 코드 + 파스칼 문자열 상수   <- C 로 옮긴 부분
  0x2690 (seg 0269)  Dos   유닛  GetTime / SetTime
  0x2710 (seg 0271)  Crt   유닛  Sound / NoSound / Delay / ReadKey / KeyPressed
  0x2D30 (seg 02D3)  Graph 유닛  BGI (InitGraph, PutImage, Bar, OutTextXY ...)
  0x60D0 (seg 060D)  System 유닛 런타임 (파일 입출력, 문자열, Halt ...)
  게임 자체 코드는 9,609바이트뿐이고 나머지는 런타임/라이브러리다.
  게임 코드는 100% 커버했다 (안 덮인 263바이트는 전부 파스칼 문자열 상수).

[자료 파일 형식 - 코드에서 알아낸 것]
  16X16.DAT   16x16 점그림 42장이 들어 있는 텍스트 파일.
              한 점이 한 글자('.'=0, '1','2','3' = CGA 색번호)이고 점 사이에 공백.
              16줄이 그림 한 장, 그림 사이에 빈 줄.
              읽어서 화면에 찍은 뒤 GetImage 로 스프라이트 42개를 만든다.
              (V1.DAT, 16X16A.DAT 도 같은 형식의 교체용 그림으로 보인다)
  B_ST.DAT    스테이지 10개의 맵.  스테이지마다
                - 11줄 x 20글자 = 타일 맵
                  '.'=1(빈칸), '0'~'9'=그 숫자 타일, '#'=먹이, 'a','b','c'=28,29,30
                - 정수 4개 (적 4마리의 속도/파라미터)
                - 정수 1개 (그 판의 먹이 개수)
              12번째 줄은 코드가 항상 3번(바닥)으로 채운다.

[게임 규칙 - 코드에서 읽어낸 것]
  맵은 20칸 x 12줄, 타일 하나가 16x16 픽셀.
  걸어다닐 수 있는 줄은 row % 3 == 2 인 줄뿐이고, 그 사이는 사다리(타일 6)로 오간다.
  이동은 대각선 점프 방식이다 - 왼쪽위/오른쪽위로 올라갔다가(0x0a/0x0e)
  왼쪽아래/오른쪽아래로 내려앉는다(0x0c/0x10).  스페이스는 제자리 점프(0x0d).
  적은 4마리, 각각 row 11/8/5/2 에 고정되어 좌우로 왕복한다.
  발밑이 빈칸(1)이면 4프레임 추락 애니메이션 뒤 죽고, 타일 7 은 즉사다.
  먹이를 다 먹으면 판 클리어.  보너스 타일 0x1c = +500, 0x1d = +1000.
  타일 0x1e 를 밟으면 움직이는 발판이 생긴다.
  스테이지 11 이 되면 1 로 돌아가면서 적 속도가 +2 씩 빨라진다(최대 0x10).
  하이스코어 초기값 30000.

[C 로 옮기면서]
  - 원본에는 심볼이 없다.  함수 이름은 **하는 일에 맞게 새로 붙였고**(LoadSprites,
    JumpMove, StageClear ...), 각 함수 위와 파일 앞머리의 [함수 목록] 표에
    원래 오프셋을 남겨 두어 바이너리와 대조할 수 있게 했다.
    전역변수도 마찬가지로 하는 일에 맞게 이름을 붙였다(player_col, stage, score,
    enemy_dir[], platform_on ...).  선언마다 원래 DS 오프셋을 주석에 적어 두었으므로
    g_XXXX 형태가 필요하면 그 표를 보고 되돌릴 수 있다.
  - 파스칼 호출 규약(인자 왼->오 push, 호출된 쪽이 정리)을 풀어서 C 인자 순서로 바꿨다.
  - 컴파일러가 넣은 스택검사/IO검사 호출은 뺐다.
  - 제어흐름은 if/while/for 로 구조화했다.  goto 는 쓰지 않았다.
  - Graph/Crt/System 함수는 파일 맨 위에 프로토타입만 선언해 두었다.
    실제로 빌드해 돌리려면 그 자리에 원하는 그래픽 라이브러리를 끼우면 된다.
    (즉 "그대로 다시 빌드되는 소스"가 아니라 동작을 읽을 수 있게 옮긴 것이다.
     gcc -fsyntax-only 로 문법 검사는 통과한다.)

[검증]
  어셈블리와 대조해 가장 크고 복잡한 네 개(proc_0B12 이동/충돌, proc_14BF 플레이어
  이동, proc_1358 칸 판정, proc_1E5B 키 입력)를 인자 순서·루프 범위·부호·분기 방향·
  배열 첨자까지 다시 확인했고, 본문은 어셈블리와 일치한다.
  그 과정에서 전역 선언 두 개(6바이트 real 을 int 로 잘못 적은 것)를 바로잡았다.

[부드럽게 움직이는 판 - bongbong_smooth.c]
  게임 로직(칸 좌표, 충돌 판정, 시간)은 bongbong.c 와 똑같다.  화면에 그리는
  방법만 바꿨다.

  1) 더블버퍼
     램에 화면 두 장(뒤 버퍼 / 배경 페이지)을 두고 뒤 버퍼에만 그린 뒤
     수직귀선에 맞춰 한 번에 화면으로 옮긴다(GfxFlip).  깜빡임과 찢김이 없다.
     "배경 페이지"에는 움직이는 것을 뺀 화면이 늘 들어 있어서, 매 프레임
     스프라이트 자국만 배경에서 되살리면 된다(GfxRestoreRect).

  2) 픽셀 단위 이동
     원본은 칸(16픽셀) 단위로 지웠다 찍었다 해서 이동이 뚝뚝 끊겼다.
     여기서는 움직이는 것마다 화면 위치를 따로 두고 목표 칸까지 시간에
     비례해 미끄러지게 한다(AcMove).  걸리는 시간은 원본이 그 칸에 머무는
     시간과 같게 맞췄다 - 적은 1000/속도 ms, 발판은 800ms, 걷기 60ms,
     대각선 점프 100ms, 추락은 한 줄에 125ms.  그래서 게임 속도는 그대로다.

  3) 스프라이트를 비침(TransPut)으로 찍는다
     원본은 16x16 네모를 통째로 덮어써서 스프라이트의 검은 여백이 뒤의
     사다리·먹이를 지웠다.  픽셀 단위로 움직이면 그게 눈에 띄므로
     색 0 은 안 찍는다.

  4) 입체감과 색 (VGA 256색)
     원본은 CGA 4색뿐이지만 화면은 이미 VGA 모드 13h(256색)다.  색마다
     어두움~밝음 4단계를 팔레트에 더 만들어 두고, 스프라이트를 읽어 들인 뒤
     테두리에 음영을 넣는다 - 빛이 왼쪽 위에서 온다고 보고 위/왼쪽은 밝게,
     아래/오른쪽은 어둡게.  1~2픽셀짜리 가는 선에는 넣지 않는다(뭉개진다).
     타일을 옆으로 이어 붙일 때 16픽셀마다 세로 줄이 생기지 않도록,
     상자의 좌우 바깥은 "속이 찬 것" 으로 친다.

  5) 걷는 모습과 꼬리 (없는 그림은 만들어 쓴다)
     원본에는 "걷는 자세"(0x0b / 0x0f - 몸을 낮춘 그림)가 그려져 있는데도
     대각선 점프 때만 잠깐 쓰고 정작 걸을 때는 안 쓴다.  그래서 그림이
     그대로 미끄러지기만 한다.

       걷는 모습 : 움직이는 동안 서 있는 자세 <-> 걷는 자세를 90ms 마다
                   번갈아 쓴다.  원래 있던 그림이라 한눈에 걷는 게 보인다.
       꼬리      : 그 위에 살짝 흔든다.  꼬리는 몸 뒤에 붙은 세로로 긴
                   덩어리라 뿌리(아래)는 두고 위로 갈수록 좌우로 많이
                   밀어(shear) 옮긴 변형을 두 장씩 만들어 43번 자리부터
                   넣고, 왼쪽-가운데-오른쪽-가운데로 WAG_MS(120ms) 마다
                   돌린다 - 초당 두 번쯤 살랑거린다.  빠르기는 그 상수만
                   고치면 된다 (걷는 자세는 POSE_MS).
                   서 있을 때도 흔든다 - 걸을 때만 흔들면 한 걸음이 짧아
                   눈에 안 띈다.  몸통은 한 픽셀도 옮기지 않는다.

                   옆모습(서기/걷기)은 꼬리를 밀지 않고 **뿌리를 축으로
                   돌린다**.  밀거나 기울이면 꼬리가 몸 앞뒤로 미끄러지는
                   것처럼 보이는데, 뿌리를 고정하고 통째로 돌리면 꼬리 끝이
                   호를 그려서 좌우로 쓸리는 것처럼 보인다.  약 ±11도와
                   ±22도 네 장을 1/256 고정소수점 sin/cos 로 만들고, 결과
                   픽셀마다 원래 자리를 거꾸로 찾아오므로 구멍이 안 생긴다.
                   사다리 자세(0x0d)는 뒤에서 본 모습이라 화면 좌우가 실제
                   좌우와 같고 꼬리도 두 다리 사이로 아래로 늘어져 있다.
                   그래서 그때만 좌우로 민다.  (TAILSRC[] 의 rot 항목)
       눈 깜빡임 : 너구리 눈은 흰자(색 3) 안에 검은 눈동자가 든 모양이다.
                   색칠하기 전 그림에서 위쪽 절반의 흰자 픽셀을 찾아 눈
                   자리를 알아내고(FindEyes), 3.4초마다 0.11초씩 그 자리를
                   살색으로 덮은 뒤 가운데에 어두운 선을 하나 긋는다.
                   그림을 따로 만들지 않고 찍은 위에 덧그리므로
                   (걷는 자세 x 꼬리 단계) 조합마다 그림을 만들 필요가 없다.
                   빠르기는 BLINK_PERIOD / BLINK_LEN 으로 조절한다.
                   사다리 자세는 뒤에서 본 모습이라 흰자가 없어 저절로 빠진다.
       적(벌레): 머리는 두고 몸통 줄들을 좌우로 한 픽셀씩 어긋나게 밀어
                   물결이 아래로 흘러가는 변형 4장씩 (8/9번).  적마다
                   위상을 조금씩 달리해서 넷이 똑같이 움직이지 않는다.

     변형 규칙은 bongbong_smooth.c 의 TAILSRC[] / WAVE_TAB[] 두 표에 있다.

  6) 스프라이트마다 다른 색
     원본은 온 화면이 청록/자홍 두 색이라 열 가지 먹이가 전부 같은 자홍색이다.
     스프라이트 종류마다 "색 1/2/3 을 무엇으로 칠할지"(테마)를 정해 두고,
     테마마다 색 3개 x 음영 4단계 = 12칸씩 팔레트를 잡는다(16번부터 204칸).

       발판 · 사다리 · 글자     원본 색 그대로 (청록/흰색)
       너구리                   주황 몸 + 짙은 빨강 귀·코 + 크림색 배
       적                       보랏빛 자홍  (플레이어와 구별된다)
       체리 빨강 / 당근 주황 / 사과 빨강 / 바나나 노랑 / 포도 보라 /
       아이스크림 크림+분홍 / 핫도그 빵색 / 수박 빨강+초록 껍질 /
       케이크 분홍 / 파인애플 금빛
       보너스 항아리와 +500/+1000  금색
       움직이는 발판             연보라
       즉사 기둥                 상아색

     테마 표는 bongbong_smooth.c 의 theme_rgb[] / spr_theme[] 두 개뿐이라
     색을 바꾸고 싶으면 거기만 고치면 된다.

     너구리 색 - 원본 CGA 에서 너구리는 몸이 자홍, 귀와 코가 하늘색, 배가
     흰색이다.  색이 넷뿐이라 그렇게 그린 것인데, 그대로 옮기면 몸만 분홍이고
     귀와 코가 하늘색으로 남아 거기만 따로 노는 것처럼 튄다.
     테마 1 을 주황 너구리로 바꿨다.
         색 1 (귀·코)  (44, 6, 0)   짙은 빨강
         색 2 (몸)     (60,28,10)   주황
         색 3 (배)     (60,56,44)   크림색
     음영 4단계는 ShadeRamp 가 이 세 색에서 자동으로 만들므로, 색을 바꾸고
     싶으면 이 아홉 숫자만 고치면 된다.  적은 보랏빛, 발판·사다리는 청록이라
     주황 너구리와 잘 갈린다.


[원본 버그 하나 고침 - 두 판 모두]
  16X16.DAT 의 그림 사이 구분줄이 파일 앞쪽에서는 빈 줄인데, 뒤쪽에서는
  "[ 16 * 16 ] : b1.dat" 같은 이름줄이고 위치도 그림 뒤에서 그림 앞으로 바뀐다.
  원본은 무조건 한 줄만 건너뛰기 때문에 23번째 그림부터 한 줄씩 밀려서,
  항아리나 떨어지는 너구리 같은 그림 위에 엉뚱한 줄이 한 줄 붙고 맨 아랫줄이
  잘렸다.  자료 줄(첫 글자가 . 1 2 3)이 나올 때까지 건너뛰도록 고쳤다
  (SkipToDotData).


[한글판 - BONGS.EXE 만]
  화면 글자를 전부 한글로 바꿨다.  글꼴은 폴더에 있는 두 개를 쓴다.

      HSMALL.FNT  조합형 8/4/4 벌식 한글 글꼴
                  글리프 360장 x 32바이트 (초성 8벌x20 + 중성 4벌x22 +
                  종성 4벌x28), 16x16 상자 안에 12x12 로 그려져 있다.
      ESMALL.FNT  로마자 글꼴 256자 x 16바이트 (실제 잉크는 5x11)

  소스의 한글 문자열은 UTF-8 그대로 두었다.  OutTextXY 가 UTF-8 을 읽어
  유니코드 음절을 초성/중성/종성으로 풀고, 조합형 글꼴에서 조각 세 개를
  꺼내 겹쳐 찍는다.  그래서 소스에 조합형/완성형 코드를 박아 넣을 필요가 없고,
  문구를 고칠 때 그냥 한글로 타이핑하면 된다.

  글자 한 줄 높이는 12픽셀, 로마자 폭 6, 한글 폭 12 이다.  원본은 8x8 이라
  글자가 커진 만큼 타이틀 화면 줄 간격과 상태표시줄 자리를 새로 잡았다.
  상태표시줄은 y 186 부터 쓴다 (바닥 타일이 한 칸 중 위 8줄만 쓰므로 그 아래가 빈다).

      최고 030000   점수 000000   시간 100   판 16   [목숨아이콘] 3

  판 번호는 원본에 없던 것이다 (원본은 오른쪽 세로줄 아래에만 나온다).
  전체 폭이 292 픽셀이 되도록 잡아 양쪽 여백 14 픽셀로 가운데 정렬했다.

  자리를 옮기고 싶으면 bongbong_smooth.c 앞쪽의 HUD_* 상수만 고치면 된다.

  타이틀 화면은 제목을 "봉봉 한글판 / VGA 개선" 으로 바꾸고, 제작자를
  "만든이: Lee T.K. (연세대 전산과 1989)" 한 줄로 합친 뒤 그 밑에
  "개선 : 하늘소 (도스박물관 2026)" 을 넣었다.  그만큼 너구리 줄과 "아무 키나 누르세요" 를
  아래로 내렸다.


[소리]  ※ 지금은 원본 그대로다 (tp.c 의 SOFT_SOUND = 0)
  아래는 켜고 싶을 때를 위해 남겨 둔 설명이다.  SOFT_SOUND 를 1 로 바꾸면 된다.

  원본은 PC 스피커에 사각파를 그냥 켰다 껐다 해서 딱딱하게 들린다.
  음과 음 사이에 틈이 없어 한 덩어리로 뭉치고, 시작·끝이 뚝 끊겨 딸깍거린다.

  PC 스피커는 켜짐/꺼짐 두 단계뿐이지만, 게이트(포트 61h 의 1번 비트)를
  귀에 안 들릴 만큼 빠르게(약 3kHz) 여닫으면 "켜져 있는 시간의 비율"로
  음량을 흉내낼 수 있다.  이걸 써서 네 가지를 넣었다.

      - 음이 바뀔 때 4ms 쉼      : 음이 또렷하게 끊긴다
      - 음 시작에 4ms 글라이드   : 딸깍임이 사라진다
      - 기다리는 동안 음량 감쇠  : 사각파의 날카로움이 죽는다
      - 긴 음에 옅은 비브라토    : 밋밋함이 줄어든다

  원본과 똑같은 소리가 기본값이다 (SOFT_SOUND = 0).


[스테이지 11~20 추가 - BONGS.EXE 만]
  원본 B_ST.DAT 에는 스테이지가 10개뿐이다.  같은 형식으로 10개를 더 만들어
  뒤에 붙였다.  원본 판(BONG.EXE)은 앞의 10개만 읽으므로 그대로 돌아간다.

  판을 만들 때 지킨 규칙 (원본 10개에서 읽어낸 것)
      줄 1            사다리칸 (위에 층이 없어 전부 '.')
      줄 2,5,8,11     걸어다니는 줄  - 아이템(# 먹이 / 7 즉사 / a,b 보너스 /
                      c 발판발생) 과 사다리('6')
      줄 3,6,9        발판 줄 - 2 왼끝 / 3 오른끝 / 4 가운데 / 5 한 칸
                      (칸 1 에서 시작하는 발판의 왼끝과 칸 19 에서 끝나는
                       발판의 오른끝은 '4' 다) / 6 사다리가 지나가는 자리
      줄 4,7,10       사다리칸
      줄 12           코드가 항상 바닥(3)으로 채운다
      사다리 하나 = 아래층 걷는 줄 w 에서 '6' 을 w, w-1, w-2 세 칸에 놓아
      w-3 층으로 이어 준다.

  11판부터는 아이템을 원본보다 조금 늘렸다.
      먹이 12~16개 (원본 10~13), 보너스 항아리 2~3개, 발판 발생 타일 1~2개
  아이템이 셋 이상 줄줄이 붙으면 가운데를 즉사 기둥으로 바꿔 끊는다.
  점프가 두 칸 건너뛰기라 기둥 하나는 넘어갈 수 있으므로, 먹이를 다 먹으려면
  한 번 뛰어넘어야 한다.

  즉사 기둥(타일 7)을 두면 안 되는 자리
      - 사다리를 타고 올라가 서는 칸, 내려와 서는 칸
        (오르내리는 도중에는 피할 수 없어 반드시 죽는다.  원본 10판도 이
         자리에는 기둥을 두지 않았다)
      - 맨 아래층 17칸부터 (너구리 출발 자리 바로 옆)
      - 이미 옆칸에 기둥이 있는 자리.  두 개가 붙으면 점프(두 칸 건너뛰기)
        로도 넘을 수 없다.  원본 10판에도 붙어 있는 기둥은 한 곳도 없다.
      - 오리가 나오는 줄에서 도망길을 막는 자리 (아래 참고)
  맨 아래층 사다리도 15칸까지만 두어 출발 자리에서 다섯 칸 이상 떨어뜨렸다.


  [한 층에 오리 두 마리를 고려한 판 짜기]

  게임에서 확인한 움직임은 이렇다.
      걷기    한 칸.  보고 있지 않은 쪽으로는 먼저 몸을 돌린다 (약 0.09초)
      점프    두 칸 건너뛰기.  가운데 칸은 건너뛴다 (약 0.25초)
              => 발판 구멍은 폭 1 만 건널 수 있다.  폭 2 부터는 못 넘는다.
      사다리  위/아래 한 칸 (약 0.08초)
      오리    자기 층의 1~19칸을 왕복한다.  구멍도 압정도 아이템도 무시하고
              걷는다.  같은 칸에 겹치면 죽고, 점프로 뛰어넘을 수도 없다
              (지나가는 두 칸을 다 검사한다).

  즉 오리를 피하는 방법은 "사다리로 그 층을 벗어나는 것" 하나뿐이다
  (줄 4,7,10 의 사다리 중간칸에는 오리가 못 온다).  맨 아래층 20칸은 오리가
  19칸에서 되돌아가므로 그 자체가 안전한 구석이다.
  한 층에 두 마리가 양쪽에서 오면 가운데 끼일 수 있으므로, 11~20판은 다음을
  지키도록 만들고 기계로 검사했다.

      1. 오리가 나오는 줄은 어느 칸에 서 있든 2수(걷기 1, 점프 2) 안에
         피난처(오르내릴 사다리 / 맨 아래층 20칸)에 닿을 수 있어야 한다.
      2. 오리가 나오는 줄의 발판에는 폭 1 구멍만 둔다.  폭 2 이상이면 줄이
         토막나서 도망칠 수 없는 구역이 생긴다.
      3. 압정을 놓은 뒤 1번을 다시 검사해서, 도망길을 막으면 물린다.
      4. 움직이는 발판(타일 c)은 오리가 없는 줄에만 둔다.
      5. 오리 속도를 낮췄다.  B_ST.DAT 의 값 4~7 을 게임이 다시 2/3 로
         늦추므로 실제로는 초당 2~4칸이다 (사람은 초당 약 11칸).
         원본 1~10판은 한 층에 한 마리라 초당 3~8칸이었다.

  [기계로 해 본 검사]
      (1) 파일 다시 읽기 - 게임과 똑같은 방식으로 B_ST.DAT 을 읽어, 출발
          자리(20,11)에서 걷기·점프·사다리로 모든 먹이에 닿는지 확인.
          11~20판 모두 통과, 닿는 칸 53~60개 (원본 49~61).
      (2) 도망길 검사 - 위 1번 규칙을 따로 짠 검사기로 다시 확인.
          11~20판 모두 "피난처까지 최악 2수".
      (3) 자동 플레이 - 게임 코드(bongbong_smooth.c)는 손대지 않고 키만
          넣어 주는 자동 조종을 붙여, 11~20판을 처음부터 끝까지 실제로
          돌려 봤다.  10판 모두 목숨 하나도 잃지 않고 클리어했고
          45~73초가 남았다 (제한 100초).
          같은 자동 조종으로 원본 1~10판을 돌리면 5,7,9,10판에서 죽는다.
          원본은 "한 마리를 앞질러 달아나는" 판이라 사다리로 숨는 이 조종
          방식과 맞지 않기 때문이다 - 새 판이 그만큼 도망갈 구석을 갖췄다는
          뜻이기도 하다.
      검사에 쓴 것 : mkstage.py(생성) / verify.py(닿는지) / safety.py(도망길)
                     / _djstub/play.c(자동 플레이).  배포물에는 들어가지 않는다.

[적이 한 걸음씩 빠뜨리던 것 - BONGS.EXE 만]
  원본은 매 초 SetTime(0,0,0,0) 으로 시계를 0 으로 되돌리면서, 적들의
  "마지막 이동 시각(enemy_last_move)" 도 같이 0 으로 밀어 버렸다.
  적은 "속도 x (지금 - 마지막이동) / 100 >= 1" 일 때 한 칸 움직이므로,
  1초가 넘어가는 자리에서 걸음 하나가 통째로 사라진다.

      속도 2칸/초 -> 초당 1칸  (절반!)
      속도 4칸/초 -> 초당 3칸
      속도 5칸/초 -> 초당 4칸

  느린 적일수록 손해가 커서, 11~20판(속도 2~4칸/초)에서는 적이 한 걸음 걷고
  쉬는 것처럼 덜컥거렸다.  시계를 되돌린 만큼(100 = 1초) enemy_last_move
  에서도 빼 주도록 고쳐서, 이제 걸음 간격이 고르다.

  다만 그렇게만 하면 적이 눈에 띄게 빨라진다(원본에서 보던 빠르기보다 빠르다).

         다) 안 되면 사다리 쪽으로 물러나 층을 벗어나고, 오리가 지나가길 기다린다

[11판부터 한 층에 적 두 마리 - BONGS.EXE 만]

[S(소리 끄기) 고침 두 가지 - 한글판만]
  1) 소리를 다시 켜도 곡이 안 나왔다.
     SetSoundOn(0) 이 VgmStop 으로 곡을 내려놓는데, 다시 켤 때는 아무도
     틀어 주지 않아서 다음 판으로 넘어갈 때까지(RestartStage) 조용했다.
     SoundToggle 에서 켜는 쪽일 때 게임 곡(BB01)을 바로 다시 튼다.
  2) "소리 켬 / 소리 끔" 안내 상자가 화면에 그대로 남았다.
     tp.c 의 그리기는 기본이 "뒤 버퍼와 배경 페이지에 같이 찍기"(GfxStatic(1))
     이고, 매 프레임 되살리는 것은 스프라이트가 지나간 자리뿐이다.  그래서
     안내 상자가 배경에까지 찍혀 아무도 지우지 못했다.
     GfxStatic(0) 으로 배경은 건드리지 않고 찍은 뒤, 700ms 가 지나면
     GfxRestoreRect 로 그 자리를 배경에서 되살린다.
     멈춤(P) 상자도 같은 병이라 같이 고쳤다.  멈춘 동안 ReadKey 로 막고
     있던 것도 KeyPressed + FrameSync 로 바꿨다 - 예전에는 멈춘 사이
     애드립이 마지막 화음을 계속 물고 있었다.

[층마다 다른 발판 색 + 사선 빛줄기 - 한글판만]
  원본 발판은 온통 한 가지 청록이라 두께도 층도 느껴지지 않는다.  256색이니
  색띠(그라데이션)를 하나 만들어 발판 한 칸(위 8줄)을 그 띠로 칠했다.
      plat_rgb[18]   거의 흰 하늘빛 -> 원본 청록(21,63,63) -> 짙은 청록
      plat_pal[18]   그 색이 들어앉을 팔레트 칸 (4..15 와 250..255 - 빈 칸)
  색 자체는 예전과 같은 청록 계열이라 화면 인상은 그대로 두고 두께만 얻었다.
      - 줄마다 두 단계씩 내려가며 짙어진다 (윗면이 빛을 받은 것처럼)
      - 왼쪽/위 가장자리는 한 단계 밝게, 오른쪽/아래는 한 단계 어둡게
        (스프라이트 음영과 같은 "빛은 왼쪽 위에서" 규칙)
      - 층마다 색띠에서 시작하는 자리를 한 칸씩 내려서(plat_off) 위층은
        밝고 아래층은 묵직하다.  발판은 3 / 6 / 9 행과 맨 아래 바닥에 있다.

  그 위에 유리에 비친 것 같은 사선 빛줄기를 얹었다.
      sh = (x + y + ph * 16) & 31
  화면에서의 가로 자리는 col*16 + x 인데 32 로 나눈 나머지만 쓰므로 칸 번호의
  홀짝(ph)만 알면 된다.  그래서 칸을 옆으로 이어 붙여도 빛줄기가 끊기지 않고
  32픽셀마다 한 번씩 비스듬히 길게 흐른다.  넓은 줄기(세 단계 밝게) 하나와
  가는 줄기(두 단계) 하나가 짝을 이룬다.

  MakePlatFrames 가 발판 그림 2~5번을 [층 4] x [홀짝 2] = 여덟 벌로 만들어
  두고, DrawStage 가 행과 칸 번호로 골라 찍는다.  원본 그림은 건드리지 않는다.


[이름은 자판으로 친다 - 한글판만]
  새 기록을 세우면 이름 세 글자를 넣는데, 예전에는 화살표 위아래로 글자를
  A -> B -> C ... 하고 한 칸씩 돌려 골라야 해서 한 글자 넣는 데도 한참
  걸렸다.  이제는 그냥 자판으로 친다.
      A~Z 0~9 빈칸 . -    치는 대로 들어가고 다음 자리로 넘어간다
                         (소문자는 대문자로 바꿔 넣는다)
      백스페이스          한 글자 지우고 그 자리로 돌아간다
      좌우 화살표         고쳐 쓸 자리 옮기기 (Del 은 그 자리만 비우기)
      엔터 / Esc          끝
  세 글자를 다 치면 자리가 끝으로 가므로, 백스페이스를 누르면 마지막 글자가
  지워진다.  그 뒤로 더 쳐도 덮어쓰지 않는다.
  쓸 수 있는 글자인지는 예전부터 쓰던 HI_SET 으로 가려서, 최고 기록 파일에
  엉뚱한 글자가 들어가지 않는다.

  [고침] 안내 글 "화살표로 글자, 스페이스로 끝" 이 상자보다 넓어서 좌우로
  삐져나왔다 (한글 한 글자가 12픽셀이라 168픽셀인데 상자 안쪽은 160픽셀).
  상자를 (48,70)-(272,162) 으로 넓히고 안내를 두 줄로 나눴다.
      새 기록입니다 !
      [ K ][ I ][ M ]            글자마다 자리와 밑줄을 두고
      이름을 치고 엔터를 누르세요   지금 칠 자리의 밑줄만 밝게
      백스페이스 = 한 글자 지우기
  검사용 층에서 화면을 그림으로 뽑아 상자 밖으로 나간 픽셀이 0개인 것을
  확인했고, 자판으로 치는 것도 여섯 가지 경우로 검사했다.
